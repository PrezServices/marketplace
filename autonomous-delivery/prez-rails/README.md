# prez rails

An autonomous delivery system for meta-repos: workflows, hand-offs and
guardrails that take a ticket to a shipped, QA-ed change. Its core rule is
that **the ticket is the contract**. An engineer curates each ticket until a
session can build it from the text alone, so anyone, engineer or not, can
drive it.

It grew out of the rails of `mattilda-education/collections`, generalized so
it doesn't depend on any one tracker, cloud or team.

## Use it

In the meta-repo:

```sh
claude plugin marketplace add PrezServices/marketplace --scope project
claude plugin install prez-rails@prezservices --scope project
```

Start Claude in the meta-repo and run `/prez-rails:setup`. It writes
`.prez-rails/` (tracker, statuses, hard stops, deploys, a page per repo) and
prepares the workspace. From the next session on, the rails load on their own.

To remove it, or to switch delivery systems: `/prez-rails:teardown`, then
`claude plugin uninstall prez-rails@prezservices --scope project`.

## The stages

| Stage | Skill | Who drives |
| --- | --- | --- |
| File a ticket | `prez-rails:create-task` | anyone |
| Make it ready | `prez-rails:curate-task` | an engineer |
| Build it | `prez-rails:implement-task` | anyone the ticket's `Driver:` line allows |
| Pre-review | `prez-rails:review-local` | the building session |
| Ship it | `prez-rails:deploy` | per the project's deploy policy |
| Prove it | `prez-rails:qa-task` | anyone |

`prez-rails:infrastructure` holds the infra and secrets rules.

## What's in here

| Path | What it is |
| --- | --- |
| `rails.md` | The always-on rules, injected at session start (a plugin can't ship a `CLAUDE.md`) |
| `skills/` | The stage skills, `setup`, `teardown`, and the vendored upstream skills |
| `trackers/` | One adapter per tracker: Linear, Jira, GitHub Issues |
| `hooks/` | Session start, plus guards: no edits in submodule folders, no sweeping adds at the root, no force push or push to `main` |
| `bin/` | `rails-new-ticket`, `rails-close-ticket`, `rails-sync`, on the Bash PATH while the plugin is enabled |
| `commands/opsx/` | OpenSpec's commands, as `/prez-rails:opsx:*` |
| `skill-overrides/` | Our changes to the vendored skills |
| `templates/` | What `setup` fills in |

## Vendored skills

`skills/` also holds copies of upstream skills, recorded in
`skills-lock.json`: Matt Pocock's ([mattpocock/skills](https://github.com/mattpocock/skills),
MIT), Cursor's `deslop` and `thermo-nuclear-code-quality-review`
([cursor/plugins](https://github.com/cursor/plugins), MIT) and OpenSpec's
`openspec-*` skills and `opsx` commands (generated by `openspec` 1.14.1).
They're used as shipped. A change to one goes in
`skill-overrides/<skill-name>.md`, which the rails tell Claude to read first.

To update them, regenerate in a scratch project and copy the result over:

```sh
scratch=$(mktemp -d) && cd "$scratch"
cp <plugin>/skills-lock.json . && npx skills update -p -y   # Matt's and Cursor's
openspec init                                               # OpenSpec's: choose Claude Code
```

Install the OpenSpec CLI at the version above first
(`npm install -g @fission-ai/openspec@1.14.1`), so the regenerated files match.

Then copy the refreshed `.claude/skills/<name>/` folders and
`.claude/commands/opsx/` into the plugin, review the diff, and open a PR.
